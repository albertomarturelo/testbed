# Milestones group executions and freeze their evidence

## Status

Accepted — 2026-11-12 (#163). Renames the run event's `release` to
`milestone` and the gate context's `release.*` to `milestone.*`
([release-gate-evaluation](2026-10-17-release-gate-evaluation.md) §1–2; the
rules are unchanged). Gives `release sign`
([git-is-identity](2026-10-15-git-is-identity.md)) its shape: closing a
milestone. [feature-tree-not-calendar](2026-10-15-feature-tree-not-calendar.md)
holds: a milestone groups executions, never cases.

## Context

When a system under test ships, the process may require evidence of the cases
executed for that version. casefile has the pieces (each run event carries
`release`, `build`, executor, result, note and evidence, and core computes the
latest result per case for gates) but no deliverable. `release` is free text,
so a typo splits a release silently, nothing opens or closes one, and a later
event changes what was "delivered". Zephyr models it as a Release grouping
executions, a case running in any number of them. The maintainer chose the
GitHub word, **milestone**: title, due date, open/closed, progress. A sprint
regression, a UAT phase or an audit is a milestone too; a release is one with
a version.

## Decision

1. **A milestone is a file** per project, `context/milestones/<slug>.yaml`:
   `title`, `state` (`open` | `closed`), `due?` (date), `release?` (the
   version or Git tag it certifies), `scope?` (a query, ADR single-query-dsl;
   default `state = active`). Closing adds `closed: { at, by, change }`.
2. **Operations, actors agent and human** (CLI, viewer, skills alike):
   `milestone open <slug>` writes the file; `milestone close <slug>` writes
   the evidence (point 4) and sets `state: closed`, in one commit. Like every
   write, they return the commit (ADR agent-runs-the-commit).
3. **Executions name an open milestone.** `run` and `ingest` take
   `--milestone <slug>`: an unknown one is `milestone.unknown`, a closed one
   `milestone.closed`, and nothing is written. A case runs in any number of
   milestones; within one, its latest result counts (gate rules unchanged).
   Run files stay where they are: a run (Zephyr's cycle) is already a group.
4. **Evidence, frozen at close:** `context/milestones/<slug>/evidence.md`,
   generated by core from the run files: the milestone, who closed it and
   when, the totals (in scope, executed, passed, failed, blocked, not run),
   the gate verdicts when `context/releases/policy.yaml` exists, then one row
   per in-scope case (ref, title, priority, latest result, executor, date,
   build, note, evidence refs) and the cases not executed. Committed, never
   regenerated: a later correction is a new milestone. Red gates do not block
   the close, but need a `note`, written into the evidence.
5. **Signed when the repository signs.** Close's commit carries
   `Casefile-Milestone: <slug>`; the human's commit uses their Git signing
   setup (`casefile init` recommends SSH signing), so the evidence shows who
   certified it. casefile never holds a key.
6. **PDF from the viewer:** a printable evidence page (print stylesheet,
   "Save as PDF"), no new dependency. A PDF built in CI waits for a real need
   and its own ADR. Attaching `evidence.md` to the GitHub Release of
   `release` is a documented CI step (`gh release upload`), not casefile's job.
7. **Viewer:** a Milestones view (list with progress "N of M executed, X
   passed", detail per case with its history in the milestone, gates, close),
   and "Record a result" picks an open milestone instead of typing a release.
8. **Rename in `0.2.0`** (already breaking): `--release` → `--milestone`, the
   event field `release` → `milestone`, `release.*` → `milestone.*` in gate
   scopes. Run files are append-only, so the loader reads an old `release`
   as `milestone`, and `--release` stays a deprecated alias until `1.0`.

## Alternatives Considered

1. **Keep `release`:** matches Zephyr and Jira, but excludes sprints, UAT and
   audits, and clashes with GitHub Releases (a tag and assets, not a group).
2. **Zephyr's Release → Cycle → Execution:** a cycle entity duplicates the run
   file, which already groups executions.
3. **GitHub milestones as the store:** ties casefile to one vendor and the
   network; files stay the source of truth (ADR files-are-source-of-truth).
   A bridge can mirror them later.
4. **Evidence on demand only:** a late event would change what was delivered.
5. **Server-side PDF now:** a rendering dependency before anyone asked for
   PDFs from CI.

## Consequences

- Issues, one session each, in order: #164 core (schema, open,
  `--milestone` checks, rename with aliases, validator); #165 evidence
  (renderer shared with #115's report, `milestone report`, close freezes
  it); #166 viewer (Milestones view, milestone picker, printable evidence);
  then the gates CLI (#47) over milestones.
- `casefile validate` reports run events naming no declared milestone as a
  warning (old free-text releases), never an error.
- The `release` work item on cases (`release:web-4.12.0`) stays a planning
  link, distinct from executions.
