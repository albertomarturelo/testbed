# milestone

A milestone groups executions, like a GitHub milestone groups issues: a
release to certify, a sprint regression, a UAT round, an audit. Each one is a
file, `context/milestones/<slug>.yaml` in its project; `casefile run` and
`casefile ingest` name it with `--milestone <slug>`, and a case runs in any
number of milestones. Closing a milestone freezes the evidence of what was
executed in it (ADR milestones-group-executions).

- **Actor:** agent, human (`report`: also CI)
- **CLI:**
  - `casefile milestone open <slug> --title <title> [--due <YYYY-MM-DD>] [--release <version>] [--scope '<query>'] [--agent <name>] [--ticket <key>] [--project <name>] --json`
  - `casefile milestone report <slug> [--project <name>] [--json]`
  - `casefile milestone close <slug> [--note <text>] [--agent <name>] [--ticket <key>] [--project <name>] --json`

  (an agent runs `open` and `close` with `CASEFILE_ACTOR=agent`; read `commit` from the `--json` output)
- **Writes:** `open`: `**/context/milestones/*.yaml` (a new file only); `close`:
  that file and `**/context/milestones/<slug>/evidence.md`; `report`: nothing

## The file

```yaml context/milestones/web-1.2.0.yaml
title: Web 1.2.0
state: open
due: 2026-10-20
release: web-1.2.0
scope: priority IN (P0, P1) and state = active
opened:
  at: "2026-10-10T09:00:00Z"
  by: qa@acme.example
  change: 3b0e8f4a-6c1d-4f7e-9a52-0d9e2c1b7a44
```

| Field | Meaning |
|---|---|
| `title` | One line, shown in the viewer. |
| `state` | `open` while executions may name it; `closed` once its evidence is frozen. |
| `due` | Optional date. |
| `release` | Optional: the version or Git tag the milestone certifies. |
| `scope` | Optional query of the cases it covers (`casefile spec query-grammar`); default `state = active`. |
| `opened` | Who opened it, when, and the change id of that commit. |
| `closed` | Written by `close`: who closed it, when, and the change id of that commit. |

The slug is the file name: letters, digits and `._-`, starting with a letter or
digit (`web-2.1.0`, `sprint-23`). `casefile validate` reports a file that does
not match this shape.

## open

1. Finds the project (`project.required`, `project.unknown`).
2. Refuses a slug the project already has (`milestone.exists`) and a `scope`
   that does not parse (`milestone.invalid_scope`, with the query error).
3. Builds the commit subject from the workspace's template (`casefile spec
   cover`, *Commit subject*): type `test`, scope the project, summary
   `open milestone <slug>`, by default `test(web): open milestone web-1.2.0`.
4. Writes the file with `state: open` and `opened`, and returns the commit of
   that one file, like `cover` (`Requested-by:`, `Agent:` unless
   `commit.agent_trailer` is `false`, `Casefile-Change:`).

Nothing is written when an error is returned.

## Naming it in an execution

`casefile run` and `casefile ingest` take `--milestone <slug>`. The milestone
must be declared and open in the case's project:

- `milestone.unknown`: no such file; the message lists the open ones.
- `milestone.closed`: it is closed; its evidence must not change.

The event stores `milestone`. Within a milestone a case's latest result counts,
as for release gates; gate scopes read `milestone.name` and `milestone.build`.

**Before `0.2.0`** the field was `release`. Old run files keep it (they are
never rewritten) and are read as `milestone`; `--release` still works as
`--milestone` with a deprecation notice in `next`, and gate scopes still accept
`release.name` and `release.build`. `casefile validate` warns about events that
name a milestone no file declares (`run.undeclared_milestone`): open it with
the same slug to group them.

## Evidence

Generated by core from the run files, the cases and `context/releases/policy.yaml`;
the same files and date give the same text. In order:

1. **The milestone:** title, slug and project, `release`, `due`, the scope,
   the latest build among its events (`milestone.build`), who opened it, and who
   closed it and when (a report says it is not closed: not frozen evidence).
2. **Totals** over the in-scope cases: in scope, executed, passed, failed,
   blocked, not run.
3. **Gates**, when the project has a release policy: each gate's verdict, the
   number of cases its scope selects, and the reasons it is red with the
   offending cases (`casefile spec query-grammar` for scopes; rules of ADR
   release-gate-evaluation, the milestone in place of the release; a triage
   counts until the day of the close).
4. **Cases:** one row per in-scope case in case order: id, title, priority,
   latest result, executor, date, build, note (the run's note on one line, cut
   at 300 characters, then its triage) and evidence refs. A case's result is its
   latest `passed`, `failed` or `blocked` event in the milestone; `skipped`,
   `not_run` and other milestones' events do not count, so such a case shows
   `not run`.
5. **Not executed:** the in-scope cases with no result.
6. **Close note**, when `close` got `--note`.

## report

1. Finds the project and the milestone (`milestone.unknown`).
2. Open: generates the evidence from the files as they are now, with today's
   date for triages, and returns it with the gates that are red now
   (`red_gates`). Closed: returns the frozen file
   (`milestone.evidence_missing` if it is gone).

It writes nothing. Without `--json` the evidence prints as a block under
`evidence:`; to keep a copy, take `value.evidence` from the `--json` output.

## close

1. Finds the project and the milestone (`milestone.unknown`); refuses a
   closed one (`milestone.closed`): a correction is a new milestone.
2. Generates the evidence as `report` does, closed now by the person at the
   keyboard (or `--requested-by` for an agent).
3. Red gates do not block, but need `--note` saying why they are accepted;
   without it, `milestone.red_gates` and nothing is written. The note goes
   into the evidence.
4. Writes `context/milestones/<slug>/evidence.md` and sets `state: closed`
   and `closed` in the milestone file, keeping its comments and key order.
5. Returns one commit of both files: subject from the workspace's template
   (summary `close milestone <slug>`, by default
   `test(web): close milestone web-1.2.0`), the trailers of `open`, then
   `Casefile-Milestone: <slug>`. A human commits as themselves, so a
   repository that signs commits signs the evidence (ADR git-is-identity).

From then on `run` and `ingest --milestone <slug>` are refused
(`milestone.closed`), and the evidence is never regenerated.

### Attaching it to a GitHub release

casefile does not upload anything. When the milestone certifies a `release`
that is also a GitHub release, a workflow step can attach the evidence:

```yaml
- name: Attach the milestone evidence
  env:
    GH_TOKEN: ${{ github.token }}
  run: gh release upload web-1.2.0 context/milestones/web-1.2.0/evidence.md --clobber
```

The job needs `permissions: contents: write`.

be), `evidence` (the Markdown), `red_gates` (open only) and `next`.

## Errors

| Code | When |
|---|---|
| `milestone.exists` | the project already has a milestone with that slug |
| `milestone.invalid_scope` | `scope` does not parse as a query |
| `milestone.unknown` / `milestone.closed` | (`run`, `ingest`) the named milestone is not declared, or is closed; (`report`, `close`) not declared; (`close`) already closed |
| `milestone.red_gates` | (`close`) a gate is red and no `--note` says why it is accepted |
| `milestone.evidence_missing` | (`report`) the milestone is closed but its evidence file is gone |
| `milestone.agent_required` / `milestone.agent_not_allowed` | as in `casefile spec cover` |
| `commit.ticket_*`, `config.commit_*` | the subject template, as in `casefile spec cover` |
| `project.required` / `project.unknown` | as in `casefile spec cover` |
| `operation.actor_not_allowed` | `open` or `close` invoked by CI |
